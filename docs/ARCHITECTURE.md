## 1. Назначение и пользовательский сценарий

Сайт — модуль из презентации этапа 1 (слайд 8, «Формирование многоконтурной
площадки», прототип в `input_data/030926_Краткая презентация этапа 1 и ТОП 5 площадок 20261016-02.pdf`).

Сценарий:

1. Пользователь выбирает **опорную площадку** из списка (17 штук).
2. Добавляет к ней **до 4 неопорных площадок** (итого комбинация до 5 площадок —
   это совпадает с ограничением методики «1–5 площадок»).
3. Сайт показывает:
   - слева — схему территории опорной площадки с легендой;
   - справа — две плашки:
     - **Рекомендуемая комбинация** — заранее рассчитанная оптимизатором;
     - **Выбранная комбинация** — то, что собрал пользователь, пересчитанное
       по той же методике.
   - отдельной вкладкой — 12 площадок, не вошедших в оптимальный набор
     (раздел 7.5).
   - в каждой плашке — миниатюры присоединённых площадок (до 4) и 4 показателя:
     индекс инвестиционного потенциала, площадь, градостроительный
     потенциал, аварийное жильё.
4. Две вкладки сценария (раздел 7.6):
   - **«Рекомендуемый сценарий»** — всё описанное выше;
   - **«Оптимизация сценария»** — выбранная комбинация поднимается наверх,
     кнопка «Оптимизировать выбор» дополняет её площадками по правилам 3.6,
     ниже появляется **расчётная комбинация**.

Пользователь — сотрудники КБ «Стрелка» и заказчика (администрация Читы).
Данные помечены в презентации как **«Конфиденциально»**. Вопрос доступа
и хостинга отложен (см. раздел 10).

## 3. Доменная модель и правила расчёта

### 3.1. Площадка (`Site`)

| Поле JSON | Столбец Excel | Ед. |
|---|---|---|
| `id` | Номер площадки КРТ (строка вида `"11.2"`) | — |
| `category` | Категория: `опорная` / `вознаграждение` / `нейтральная площадка` / `обременение` | — |
| `areaHa` | Размер территории | га |
| `ip` | Индекс инвестиционного потенциала | — |
| `avarM2` | Аварийный жилой фонд | м² |
| `gradM2` | Градпотенциал | м² |
| `sppNewM2` | СПП новой жилой застройки | м² |
| `sppDemolM2` | СПП прочей сносимой застройки | м² |
| `name` | (нет в Excel, см. 2.1) | — |
| `image` | путь к миниатюре | — |

Справочно: 17 опорных, 63 неопорных. Из неопорных 15 крупнее 45 га
и **не могут быть присоединены** ни к какой опорной. Остаётся 48 площадок,
которые можно добавлять: 27 нейтральных, 14 обременений, 7 вознаграждений.

### 3.2. Правила методики для одной комбинации (перенос из `krt_optimizer`)

Комбинация = 1 опорная + 0…4 неопорных площадок.

| Правило | Формула | Тип |
|---|---|---|
| Площадь | `Σ areaHa ≤ 45` | жёсткое (UI не даёт нарушить) |
| Размер | `1 ≤ n ≤ 5` | жёсткое (UI не даёт нарушить) |
| Состав | ровно одна опорная; неопорные площадью > 45 га запрещены | жёсткое |
| Интегральный IP | `IP = Σ(ip·area) / Σ area`, проходит только `IP > 1` строго | **мягкое на сайте**: комбинацию с IP ≤ 1 можно собрать, значение показывается с пометкой «не проходит методику» |
| Предельные эффекты | Δ = сумма показателя **только по присоединённым** площадкам | расчёт |
| Крупная опорная (31.4, 52.6 га) | самостоятельная, присоединять нельзя | особый случай UI (7.3) |

**Точность сравнения с 1.** В данных есть площадки с IP ровно 1.00
(15.3, 19.1, 20.1). Сравнение `IP > 1` на числах с плавающей точкой может
дать ошибку на границе. Проверка выполняется в целых числах, как в
оптимизаторе:

```
valid ⇔ Σ (round(ip·100) − 100) · round(area·10) > 0
```

Само значение IP для отображения считается обычным делением.

### 3.3. Показатели плашек

| Показатель | Формула | Формат |
|---|---|---|
| Индекс | интегральный IP | **2 знака** (`1,23`), и у комбинации, и у площадки. **Риск:** у 3 из 16 рекомендуемых (IP 1,0017; 1,0020; 1,0037) показывается «1,00», хотя они проходят; выбранная с IP 0,996 тоже покажет «1,00», но не проходит. Статус IP > 1 всегда берётся из целочисленной проверки и показывается словами («не проходит методику», «проходит» в блоке проверки). Ожидается дальнейшая правка индекса от заказчика |
| Площадь участков, га | `Σ areaHa` | 1 знак |
| Градостроительный потенциал, тыс. м² | `Σ gradM2 / 1000` | целое |
| Аварийное жильё, тыс. м² | `Σ avarM2 / 1000` | 1 знак |

**Решено:** суммы считаются по **всей** комбинации, включая опорную.
Градпотенциал просто суммируется. Оптимизатор градпотенциал не учитывал,
поэтому выбор пользователя может обгонять рекомендацию по этому показателю.
Это ожидаемо и принято. Предельные эффекты (Δ только по присоединённым)
показываются во всплывающей подсказке или второй строкой.

### 3.4. Рекомендуемая комбинация

- Источник: `output/KRT_оптимизация_результат.xlsx`, лист «Итог».
  Набор **заморожен**: при сборке читается файл, во время работы сайта
  оптимизатор не запускается.
- Причина заморозки: у задачи несколько равнозначных оптимумов, CP-SAT может
  вернуть другой при смене версии OR-Tools. Рекомендация не должна «плавать».
- У 16 опорных есть рекомендуемая обычная комбинация. У 31.4 (52,6 га)
  рекомендуемой комбинации нет: площадка рассматривается самостоятельно.
- **Смысл рекомендации для пользователя:** это часть глобально оптимального
  разбиения всех 80 площадок, а не лучшая комбинация для этой опорной в
  отдельности. Пользователь может собрать вариант с бо́льшим IP для одной
  опорной, «забрав» площадку у другой. **Это нормально и принято**:
  оптимизация строилась так, чтобы распределить все площадки. На сайте это
  объясняется одной фразой под заголовком плашки.

### 3.5. Подсказки о конфликтах (желательно, этап 2)

Если пользователь добавляет площадку, которая в рекомендуемом наборе
закреплена за другой опорной, показать: «В рекомендуемом наборе 17.2
закреплена за 11.2». Если площадка не вошла в оптимальный набор
(12 площадок), показать причину из листа «Не вошли».

### 3.6. Оптимизация выбора (вкладка «Оптимизация сценария»)

Локальная задача для одной опорной, **не** пересчёт глобального набора:
`krt_optimizer/` и принятый набор не меняются.

- **Вход:** опорная + все выбранные площадки (их пользователь «точно оставляет»).
- **Кандидаты:** основной список присоединяемых (43), без выбранных.
  Площадки из «Не вошли» не берутся. Площадки, закреплённые в рекомендации
  за другими опорными, **брать можно**: в карточке показывается, за кем они закреплены.
- **Ограничения:** как в 3.2: ≤ 45 га, ≤ 4 присоединённых, IP > 1 строго (в целых).
  Можно занять не все свободные места, если так лучше, в том числе ни одного.
- **Критерии — лексикографические цели методики**
  (`input_data/Промпт_воспроизведение_оптимизации_КРТ.md`, п. 4), перенесённые
  на одну комбинацию:
  1. охват: больше площадок в комбинации;
  2. компактность (min максимального размера): при зафиксированном охвате
     на одну комбинацию не влияет;
  3. Парето по трём эффектам: обеспечивается шагами 4–6;
  4. Δ аварийного фонда ↑; 5. Δ новой жилой застройки ↑; 6. Δ прочей сносимой ↓
     (Δ — по всем неопорным площадкам комбинации, как в методике, п. 3);
  7. меньшие ID в естественном порядке — только для однозначности.
  Градпотенциал в подборе **не участвует**, как и в методике.
- **Согласованность:** рекомендуемая комбинация допустима для подбора, поэтому
  подбор с пустым выбором не хуже её по целям 1–6 (проверяет pytest).
- **Статусы:** `ok` (в т. ч. «добавить нечего»), `full` (уже 4 присоединённых),
  `standalone` (опорная > 45 га), `infeasible` (с оставленными IP > 1 недостижим).
- **Реализация:** перебор с отсечением по площади в браузере
  (`web/js/domain/optimize.js`, ≤ ~137 тыс. вариантов, миллисекунды).
  Эталон — `tools/optimize_reference.py`, **другой алгоритм** (перебор
  `itertools.combinations`), golden-кейсы в `tests/golden_cases.json` → `optimize`.
  Пара файлов меняется только вместе.

## 4. Архитектура верхнего уровня

**Решение: статический сайт + Python-сборка данных. Бэкенда нет.**

```
 ┌──────────── сборка (Python, на машине аналитика) ────────────┐
 │                                                              │
 │  параметры площадок.xlsx ─┐                                  │
 │  KRT_..._результат.xlsx ──┼─► tools/build_data.py ─► web/data/sites.json
 │                           │        │  (валидация,            web/data/recommended.json
 │                           │        │   алиасы, проверки)     tests/golden_cases.json
 │  parcels/*.pdf ───────────┴─► tools/build_images.py ─► web/img/parcels/<id>.webp
 │                                      └─► build/images.json (размеры, масштаб) ─► build_data.py
 │                                                              │
 └──────────────────────────────────────────────────────────────┘
                                │  копирование папки web/
                                ▼
 ┌──────────── рантайм (браузер) ───────────────────────────────┐
 │  index.html + css + js (ES-модули, без фреймворка)           │
 │  fetch(sites.json, recommended.json) → расчёт в браузере     │
 └──────────────────────────────────────────────────────────────┘
                                ▲
             nginx (HTTPS, заголовки безопасности, доступ по паролю/VPN)
```

Почему так:

- Расчёт для одной комбинации — это несколько сумм и одно деление на
  ≤ 5 площадках. Серверу нечего делать.
- Нет сервера, базы и API → почти нет поверхности атаки. Взламывать нечего,
  кроме веб-сервера со статикой.
- Нет npm-зависимостей в рантайме → нет атак через цепочку поставок.
- Данные — 80 строк, ≈ 20 КБ JSON.
- Хостинг: любой nginx, проще всего в эксплуатации.

Цена решения: формулы есть и в Python (`krt_optimizer/models.py`), и в JS.
Защита от расхождения — «золотые» тесты (раздел 11): Python генерирует
набор комбинаций с эталонными результатами, JS-тесты обязаны их воспроизвести.

Когда пересмотреть решение: если понадобятся учётные записи, сохранение
вариантов на сервере или запуск оптимизатора из интерфейса. Тогда
добавляется FastAPI-сервис, который переиспользует `krt_optimizer`.

```json
      "imageWidthM": 1165.4,
      "addable": false,
      "reason": null
    }
  ]
}
```

`addable` = неопорная и `areaHa ≤ 45`, вычисляется при сборке.
`imageSize` / `thumbSize` — пиксели WebP (для `width`/`height` без скачков вёрстки),
`imageWidthM` — реальная ширина кадра в метрах, из неё строится масштабная линейка (раздел 9).
м² записываются целыми числами.
`reason` — причина с листа «Не вошли» (7.5) или `null`. Площадки с
непустым `reason` показываются во вкладке «Не вошли», остальные
присоединяемые — в основном списке.

### 6.2. `web/data/recommended.json`

```json
{
  "source": "KRT_оптимизация_результат.xlsx",
  "coverage": 68,
  "total": 80,
  "byAnchor": {
    "11.2": { "type": "regular", "additional": ["17.2", "20.4", "16.3"] },
    "31.4": { "type": "standalone", "additional": [] }
  },
  "notIncluded": { "20.2": "Нет ни одной допустимой комбинации…" }

```

Только состав. Показатели на сайте всегда пересчитываются той же функцией,
что и для выбранной комбинации. Это гарантирует, что обе плашки считаются
одинаково. Скрипт сборки сверяет пересчёт с числами из Excel и падает при
расхождении.

## 7. Фронтенд

### 7.1. Технологии

- HTML + CSS + JavaScript (ES-модули), **без фреймворка и сборщика**.
  Один экран, 80 элементов, 2 списка, 3 панели. React/Vue здесь добавят
  вес и зависимости без пользы.
- Типизация через JSDoc + `// @ts-check` (проверяется редактором, не
  требует сборки).
- Node.js нужен **только разработчику** для тестов (`node --test`) и,
  при желании, линтера. На сервер не попадает. Сейчас Node на машине не
  установлен.

### 7.2. Модули и потоки

```
URL ?a=11.2&s=17.2,20.4  ─► state.js ─► main.js ─► domain/combo.js (расчёт)
                               ▲            │
         клики в списках ──────┘            └─► ui/* (рендер через textContent)
```

- **Состояние** = `{ anchorId, selectedIds[] }`. Всё остальное вычисляется.
- **URL** хранит состояние и вкладку сценария (`&tab=opt`): ссылку на вариант можно переслать коллеге.
  Параметры из URL проверяются по белому списку ID. Неизвестное отбрасывается.
- `domain/combo.js` — чистые функции без DOM. Единственное место с
  формулами на фронте. Площадь сравнивается в десятых гектара, IP в сотых:
  лимит 45 га и порог IP = 1 проверяются точно.
- Состояние вида (вкладка, фильтр категории) не влияет на расчёт и в URL
  не пишется.
- Отрисовка: панель целиком перестраивается при каждом изменении через
  `renderInto`, который сохраняет прокрутку и фокус (по `data-key`).
- Сообщения («не помещается: осталось X га», снятые при смене опорной,
  «закреплена за …» из 3.5) показываются в live-регионе `role="status"`.
- Неактивные строки списка — `aria-disabled`, а не `disabled`: остаются
  в фокусе, клик объясняет причину.
- В плашке «Рекомендуемая» кнопка «Перенести в выбранную», в «Выбранной» —
  снятие площадки (×) и «Сбросить выбор».

### 7.3. Состояния интерфейса

| Ситуация | Поведение |
|---|---|
| Ничего не выбрано | Подсказка «Выберите опорную площадку», плашки пустые |
| Выбрана опорная, добавленных нет | Выбранная комбинация = одна опорная, показатели считаются |
| Добавление превысит 45 га | Площадка в списке неактивна, подсказка «не помещается: осталось X га» |
| Уже 4 добавленных | Остальные неактивны |
| IP ≤ 1 | Комбинация разрешена. Значение индекса выделено, пометка «не проходит методику: IP ≤ 1» |
| Опорная 31.4 | Список добавления заблокирован. В плашке «Рекомендуемая комбинация» текст: «Рекомендуемых комбинаций нет: площадь участка больше 45 га, он рассматривается самостоятельно». Выбранная комбинация = только 31.4 |
| Смена опорной | Добавленные площадки, которые не помещаются в новый бюджет, снимаются с уведомлением |
| Ошибка загрузки данных | Сообщение об ошибке, без падения страницы |

### 7.4. Какие площадки предлагать для добавления

**Решено:** неопорные площадью ≤ 45 га с фильтром по категории.
Основной список — 43 площадки, ещё 5 присоединяемых лежат во вкладке
«Не вошли». Прототип (только обременения) не обязателен.

### 7.6. Вкладки сценариев

| | «Рекомендуемый сценарий» (по умолчанию) | «Оптимизация сценария» (`?tab=opt`) |
|---|---|---|
| C1 | Рекомендуемая (розовая) + «Перенести в выбранную» | Выбранная (жёлтая) + **«Оптимизировать выбор»**, «Сбросить выбор» |
| C2 | Выбранная (жёлтая) | **Расчётная** (голубая): оставленные + добавленные (бейдж «+», обводка) + «Перенести в выбранную» |
| C3 | Выбранная минус рекомендуемая | Расчётная минус выбранная |

- Результат оптимизации не хранится в URL и действителен только для того
  выбора, для которого посчитан: любое изменение выбора возвращает C2
  к приглашению нажать кнопку.
- **Раскладка не зависит от вкладки и состояния:** в плашках всегда 3 строки
  под пояснения, ряд из 4 миниатюр (сообщение — поверх пустого ряда), строка
  под предупреждение IP и ряд кнопок в одну строку; подсказка вкладки — 2 строки;
  блок сравнения в C3 выводится всегда (прочерки без данных). Иначе менялась
  высота рядов сетки и вместе с ней масштаб схемы опорной.
- Тексты статусов: `full` — «Оптимизировать нечего: выбрано 4 площадки, это
  максимум. Оставьте важные для вас площадки, остальные уберите, и мы
  подберём более подходящие»; `standalone`, `infeasible` — с объяснением, что делать.

### 7.5. Вкладка «Не вошли»

Вторая вкладка рядом со списком добавляемых площадок. Состав берётся
**из листа «Не вошли»** принятого результата
`output/KRT_оптимизация_результат.xlsx`: 12 площадок, у каждой причина
из того же листа.

| Группа | Площадки | Причина (из Excel) |
|---|---|---|
| Больше 45 га и IP ≤ 1 | 18.5, 26.1, 26.2, 27.1, 29.2, 30.1, 35.1 | не допускается как самостоятельная площадка |
| До 45 га, IP = 0 | 20.2, 27.3, 27.5, 27.6, 30.2 | нет ни одной допустимой комбинации с её участием |

Самостоятельные крупные площадки с IP > 1 (33.2, 21.1, 15.2, 10.1, 16.1,
32.1, 19.2, 34.2) **в эту вкладку не попадают**: они входят в оптимальный
набор. Присоединить их нельзя, поэтому в списке добавления их тоже нет.

Площадки второй группы по площади присоединяемы. Пользователь может
добавить их из вкладки, но индекс комбинации тогда гарантированно
окажется ≤ 1, и плашка покажет пометку «не проходит методику».

- Надзаголовок «Мастер-план реализации проектов КРТ», заголовок «Чита»,

  - Фоллбэки: без `backdrop-filter` и при `prefers-reduced-transparency` —
    почти непрозрачный белый; при `prefers-reduced-motion` — без анимации.

промежутки). Блоки занимают целые ячейки или их объединения:

```
ряд 1 │ Опорные площадки   │ Выбранная опорная: │ Рекомендуемая      │
```

## 9. Изображения площадок

Исходные PDF векторные, единого масштаба, миниатюрные площадки
теряются. Конвейер `tools/build_images.py` (pypdfium2 + Pillow):

1. Пробный рендер (×4) с прозрачным фоном, граница по альфа-каналу + поля 5 %
   (не меньше 2 pt).
2. Повторный рендер только кадра с масштабом под целевой размер (до ×80):
   PDF векторные, поэтому крошечные площадки (23.2, 0,5 га) остаются чёткими.
3. Два варианта: схема (длинная сторона 1200 px) и миниатюра (320 px).
   WebP **lossless с прозрачностью**: lossy выигрывает лишь 5–25 %, а
   страница за раз грузит одну схему (≤ 180 КБ) и до 8 миниатюр.
4. **Масштаб в метрах.** Все PDF в одном масштабе, поэтому
   `м/pt = √(Σ площадь из Excel, м² / Σ закрашенная площадь, pt²)`.
   Для 80 площадок получилось 12,25 м/pt, у крупных площадок отношение
   стабильно (разброс 146–152 м²/pt²). В JSON — ширина кадра в метрах,
   UI рисует линейку (5 м … 2 км, не длиннее 30 % кадра) и подпись площади.
5. 32.1 касается края листа, сборка пишет предупреждение.

Сырые PDF на сервер **не выкладываются**.

Цвета легенды (сняты с PDF):

| Слой | Цвет |
|---|---|
| Свободные участки | `#77C8D2` |
| Участки расселяемой аварийной застройки | `#F192B0` |
| Участки редевелопмента | `#748FC9` |
| Участки объектов социальной инфраструктуры | штриховка |
| Участки сохраняемых существующих ОКС | `#E8EAEB` |

Изображения есть для всех площадок из Excel, и опорных, и добавляемых:
схема опорной и миниатюры в плашках берутся из `parcels`.

## 10. Безопасность

Подробный чек-лист — скилл `.claude/skills/krt-web-security`. Главное:

1. **Доступ — отложено.** Данные помечены «Конфиденциально», но способ
   закрытия (пароль, VPN) и хостинг решаются позже. До решения сайт не
   выкладывается в открытый интернет. `X-Robots-Tag: noindex` ставится сразу.
2. **Статика без сервера приложений.** Нет форм, API, базы.
3. **Content-Security-Policy** без `unsafe-inline` и `unsafe-eval`, всё
   с собственного домена (`default-src 'self'`), `frame-ancestors 'none'`.
4. **Никакого `innerHTML`** с данными. Только `textContent` и `createElement`.
5. **Нет внешних CDN**, шрифтов Google, счётчиков. Всё локально.
6. **Параметры URL** проверяются по белому списку ID.
7. Заголовки: HSTS, `X-Content-Type-Options: nosniff`,
   `Referrer-Policy: no-referrer`, `Permissions-Policy` с запретами.
8. В `web/` не попадают исходные Excel, PDF, `.git`, `.venv`, source maps.
9. Python-зависимости сборки зафиксированы по версиям в `requirements.txt`.

## 16. Скоринговая модель (`scoring.html`)

### 16.1. Что это

Интерактивная карта оценки территории Читы на гексагональной сетке 200 м
(15 372 ячейки) по двум профилям — **город** (13 критериев) и **инвестор**
(14 критериев, критерий 16 исключён), с вкладками «Весь город / Площадки КРТ»,
«Город / Инвестор / Общий», весами критериев 1–10 и рейтингом 80 площадок.
Пересобрана из итоговой `krt_map_updated.html` проекта коллеги (генератор
`generate_map.py`) без изменения алгоритмов, разметки и вида панели;
сверху добавлена шапка сайта.

### 16.2. Исходники (`scoring/`) и сборка

| Файл | Роль |
|---|---|
| `krt_scores_city_criterion12_inverted.gpkg` | баллы города (у города инвертирован критерий 12) |
| `krt_scores_investor_without_16.gpkg` | баллы инвестора без критерия 16 |
| `Площадки КРТ в МСК 75.gpkg` | контуры площадок (87, показываются 80) |
| `Копия Мастер-презентация _ КРТ Чита - График 156.xlsx` | лист «Матрица площадок»: градпотенциал, исходные статусы |
| `Критерии.xlsx` + `crt_pipeline.py` | подписи и направления критериев (методика коллеги, **закрыта**) |
| `README_методика_скоринга.md` | описание расчёта баллов (конвейер пересчёта удалён: слои лежали на диске G:) |

`tools/build_scoring.py` переносит логику `generate_map.py`: правки подписей
для карты, упрощение гексов на 40 м, округление баллов до 3 знаков, признак
`_in_krt` (intersects), средние баллы гексов по площадкам (intersects,
по упрощённой геометрии). Выход — `web/data/scoring/`:

| Файл | Содержимое |
|---|---|
| `hexes.json` | `hexId[]`, `inKrt[]`, `rings[]` — геометрия общая для профилей |
| `profiles.json` | по профилю: `label`, `sheet_name`, `layers[]`, `scores{crit_*: []}` |
| `plots.json` | GeoJSON 80 площадок: номер, адрес, площадь, градпотенциал, `criteria_city/investor` |
| `map-config.json` | адрес тайлов Mapbox с токеном из `.env` или `null` (в .gitignore) |

Объём 4,8 МБ вместо 23 МБ исходного HTML. Сборка проверяет: одинаковые
`hex_id` и геометрия у профилей, 13 / 14 критериев, 80 площадок, токен только
публичный (`pk.`).

### 16.3. Алгоритмы (`web/js/scoring/model.js`, закрыты)

- Интеграл профиля: Σ(балл × вес) / Σвес по непустым критериям, округление
  до 3 знаков, min–max 0–10. Вес по умолчанию 5.
- Общий слой: (интеграл города × вес + интеграл инвестора × вес) / Σвес,
  повторная min–max 0–10. Веса по умолчанию: инвестор 6, город 4.
- Площадки: интеграл профиля по средним баллам гексов площадки → min–max;
  терцили (≥ 2/3 — «Высокая», < 1/3 — «Низкая») → динамический статус
  (4 статуса) → итог = взвешенное среднее города и инвестора → min–max →
  место с учётом равенства; выгрузка рейтинга в Excel (SpreadsheetML).
- Цвет: 10 опорных цветов с линейной интерполяцией; балл 0 — без заливки.
- Меняются только с пересъёмом эталона: `tests/scoring_golden.json` снят с
  функций исходной страницы (2 набора весов: интегралы всех гексов, общий
  слой, рейтинг); `tests/scoring.test.js` обязан его воспроизвести.

### 16.4. Отличия от исходной страницы (только техника)

- Данные, шрифты и Leaflet вынесены из HTML в файлы; Leaflet — `web/vendor/`.
- Без `innerHTML`, inline-обработчиков и inline-стилей: DOM и подсказки
  строятся через `createElement`, бывшие `style="…"` — классы в `scoring.css`.
- Ошибка загрузки — сообщение поверх карты, а не подмена содержимого.
- Шапка сайта над картой; панель, цвета `#028BA8`, шрифт — без изменений.

### 16.5. Безопасность

- CSP для `scoring.html`: `img-src 'self' https://api.mapbox.com https://*.tile.openstreetmap.org`,
  остальное как у сайта. В nginx — через `map $uri` (`deploy/nginx.conf`).
- Referrer-Policy для карты `strict-origin`: токен Mapbox с ограничением по
  домену проверяется по Referer; путь и параметры не уходят.
- Токен — только публичный `pk.`; секретный `sk.` сборка отвергает.
